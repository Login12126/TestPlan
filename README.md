# План автоматизации тестирования сценария перехода к форме записи и заполнения формы

**Сайт:** [netology.ru](https://netology.ru)

---

## 1. Цель работы

Цель данного плана — определить состав, подход и ресурсы для автоматизации тестирования ключевого пользовательского
сценария на сайте Нетологии: **переход к форме записи, заполнение формы и проверка корректной передачи данных в API при
отправке заявки**.

План ориентирован на:

- Проверку корректности работы формы.
- Валидацию полей.
- Интеграцию с API.
- Устойчивость пользовательского пути.
- Минимизацию рисков регрессий при дальнейшем развитии продукта.

---

## 2. Перечень автоматизируемых сценариев

### 2.1. Данные для тестирования

Валидные данные используются как базовые входные данные для позитивных сценариев и могут применяться повторно.

- **Имя:** Иван Иванов
- **Email:** ivan.petrov@example.com
- **Телефон:** +79991234567
- **Комментарий:** Хочу записаться на курс

Общая характеристика валидных данных:
- корректные значения без запрещённых символов;
- соответствуют типовым пользовательским вводам;
- достаточной длины;
- подходящего формата.

Невалидные данные описываются отдельно для каждого негативного сценария, чтобы точечно проверять конкретное правило валидации.

Общая характеристика невалидных данных:
- значения с ошибками формата;
- пустые значения;
- слишком короткие или слишком длинные строки;
- недопустимые символы;
- некорректные email и телефоны;
- значения, нарушающие правила валидации.

## 4. Перечень необходимых разрешений, данных и доступов

- Доступ к **тестовому окружению** сайта.
- Разрешение на выполнение **автоматизированных прогонов** по целевым страницам.
- Доступ к **требованиям на форму записи**, включая список полей, правила валидации, тексты сообщений об ошибках и
  сценарий API-обработки.
- Доступ к **спецификации API**: endpoint, методы, схема запроса и ответа, коды ошибок.
- Доступ к **макетам или спецификации интерфейса** для проверки соответствия формы ожидаемому виду.
- **Тестовые данные**: email-адреса, номера телефонов, имена и другие значения для позитивных и негативных сценариев.
- Доступ к **логам, аналитике, backend-ответам**, если требуется подтверждать факт обработки заявки.
- Согласование допустимой **частоты и времени запуска автотестов**, чтобы не мешать работе сайта и пользователям.
- При необходимости — доступ к **API**, тестовым токенам или учетным данным для безопасной проверки интеграции.



## 5. Перечень и описание возможных рисков при автоматизации

| Риск                                | Описание                                                                                                           |
|-------------------------------------|--------------------------------------------------------------------------------------------------------------------|
| **Изменение интерфейса**            | Небольшие изменения верстки могут привести к падению тестов из-за неактуальных локаторов                           |
| **Динамическая загрузка элементов** | Форма может открываться с задержкой, что создаст нестабильность при выполнении тестов                              |
| **Защитные механизмы сайта**        | CAPTCHA, антибот-защита или ограничение частоты запросов могут препятствовать автоматическому выполнению сценариев |
| **Отсутствие тестового стенда**     | Запуск автотестов на production-среде повышает риск воздействия на реальных пользователей                          |
| **Зависимость от внешних сервисов** | Сбой CRM, почтового сервиса или API может вызвать ложное падение тестов                                            |
| **Недостаток тестовых данных**      | Повторное использование одних и тех же email или телефонов может мешать повторяемости сценариев                    |
| **Изменение бизнес-логики**         | Появление новых обязательных полей, изменение правил валидации или схемы API потребует обновления тестов           |
| **Флаки-тесты**                     | Сетевые задержки, анимации и нестабильность рендера могут приводить к нестабильным результатам                     |
| **Ошибки контрактов API**           | Несоответствие полей, типов или кода ответа между frontend и backend может ломать интеграцию                       |
| **Недоступность backend**           | При сбое серверной части UI может показывать некорректный статус, а тесты — падать без реальной причины            |

## 8. Заключение

Предложенный набор автотестов покрывает как **пользовательский путь** на сайте Нетологии, так и **проверку
API-интеграции** при отправке формы. Такой подход повышает надежность проверки, помогает выявлять ошибки на UI- и
backend-уровнях и снижает риск регрессий в критичном сценарии записи.

Автоматизация позволит:

- Сократить время ручного тестирования.
- Увеличить покрытие и частоту проверок.
- Обеспечить стабильность ключевого конверсионного пути.
